Flow 03

Documents & threads

Threads are the only discussion primitive — no comments, no proposals. They can be doc-level or anchored to a CRDT range. Display fields (line, excerpt) are advisory; the truth is the anchor, computed from Yjs relative positions.

Purpose

Lets a human (or agent CLI) start a conversation tied to a specific piece of text, with the anchor surviving edits — because the anchor is a CRDT relative position, not a character offset.

User experience

  • Selecting any text shows a floating action bar with "Open thread" as the primary action, beside basic formatting.
  • Clicking it opens an inline drafter beside the selection, prefilled with a quoted snippet of the range.
  • The user types a message, optionally @-mentions humans or agents, and posts.
  • On post: the range highlight gets a permanent thread badge. The new thread appears in the right pane (selected) and in the line gutter.
Triggers
• Selection: any text selection of ≥ 2 chars shows the floating bar; ⌘/ opens the drafter without the bar.
• Open thread (no selection): the right-pane "+" button creates a doc-level thread (no anchor).
• Post: ⌘↵ or click "Open thread" → creates the thread and clears selection.
• Mention: typing @ opens an autocomplete with humans + agents in this workspace.

Features for engineering

  • Capture the selection as a Yjs relative position pair (start, end) immediately at selection-time; persist that to the backend on submit.
  • Optimistic create: render the thread locally with a temp ID; reconcile on server response.
  • Excerpt field (≤ 80 chars) is sent for display fallback only; range remains authoritative.
  • Server may resolve the anchor server-side later for diff inboxes; client doesn't trust the line number across edits.

Purpose

One thread, end to end. Humans and agents speak in the same chronological list — agent messages are tinted, never hidden. Anchor is visible and clickable so context is never lost.

User experience

  • Opens in the right pane (over the thread list) when a thread is selected. Sticky header with anchor; sticky composer at bottom.
  • "Jump to range" scrolls the editor to the anchored span and flashes it briefly.
  • Composer supports @ mentions; mentioning an agent puts the message in their for-me inbox (Flow 06).
  • Agent messages are styled with the agent tint but use the same bubble grammar as human messages — emphasis is on collaboration, not species.
Triggers
• Open thread: click a row in the right-pane Threads list, or click a range highlight in the editor, or click a line-gutter chip.
• Reply: ⌘↵ or click "Reply" → POST /api/threads/:id/messages.
• Mention agent: creates a for-me inbox event for that agent.
• Jump to range: resolve the relative position to current Y state, scroll editor, flash highlight.
• Resolve / mute / archive: overflow menu (top-right); resolved threads collapse with a "View resolved" toggle in the list.

Features for engineering

  • Messages stream via WS or SSE — same channel as activity. New messages animate in.
  • Optimistic send, with retry button if the message fails.
  • Mentions are stored structurally (target type + ID), not parsed from text at render time.
  • Anchor resolution: the editor resolves the relative position once when the thread opens; if the range is "lost" (deleted content), show a "anchor moved/removed" pill with the original excerpt.

Purpose

Multiple threads can anchor to the same line. This affordance prevents pile-ups and gives a "what's been said about this" view that doesn't require leaving the doc.

User experience

  • Lines with ≥ 1 thread show a small chip after the line: "N threads".
  • Hovering the chip opens a popover summarizing each thread (most recent first); the line is also softly highlighted in the gutter.
  • Clicking a thread opens the right-pane detail; the chip stays so the user can come back.
  • "Start new thread" creates a doc-level-but-line-pinned thread on this line.
Triggers
• Hover chip: opens summary popover.
• Click row: opens thread detail.
• Keyboard: ⌥T while caret is on a line cycles through that line's threads.

Features for engineering

  • Thread-counts-by-line are computed by resolving each thread's anchor against the current Y doc. Cache per render frame.
  • Gutter chip is virtualized along with the editor lines; never render off-screen chips.
  • "Resolved" threads dim but are not hidden; toggle in popover to hide.

Engineering spec — full surface

APIs (BE)

GET /api/threads/:id/messages?after=cursor
Anchor model
Range threads store Yjs relative positions for start and end. Server keeps them opaque; the client resolves them against the current doc state to compute current absolute positions. Never trust the cached line number across edits.
Mentions
Stored as {type: 'user'|'agent', id, handle_at_insert}. Mentioning an agent enqueues a thread.mention event on that agent's for-me inbox (Flow 06).
Components
<SelectionToolbar> · <ThreadDrafter> · <ThreadList> · <ThreadDetail> · <ThreadMessage> · <GutterThreadChip> · <MentionAutocomplete>.
Realtime
New messages and new threads are broadcast over the workspace SSE/WS channel. The active doc's threads tab updates live; non-active threads bump a count badge in the sidebar.
Editor integration
TipTap + y-prosemirror. A custom ThreadAnchorMark decorates ranges that have at least one open thread. Anchored highlights are rendered as ProseMirror decorations, not stored marks.
Edge cases
Anchor lost (range deleted) → display a non-modal "anchor removed; original excerpt preserved" tag in thread detail. Cross-doc references (a thread mentions another doc) are rendered as inline links.
